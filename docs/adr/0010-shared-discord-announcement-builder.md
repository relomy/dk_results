# Consolidate Discord announcement formatting into one shared builder

Discord contest messages formatted inconsistently depending on which part of the system sent them: `lobby/formatting.py`, `completion_processor.py` (warning/live/completed and soft-finish), `notifications/bonus_announcements.py`, and inline formatting in `bot/discord_bot.py` each owned their own layout, so an emoji, a sheet link, or a bulleted-vs-flat structure could drift independently per call site.

`discord_announcements.py` now owns the shared chrome (sport emoji, header line, bulleted detail lines, inline sheet link) for all 6 push-notification kinds — contest-warning, live, completed, soft-finish, bonus-achievement, double-up-found — via one `build_*` function per kind. Each builder accepts only the fields relevant to its kind (bonus-achievement has no sheet link or entry fee; double-up-found has no relative-time field); nothing is forced to emit a placeholder for a field it doesn't have. `DISCORD_ROLE_MAP` and the canonical `SPORT_EMOJI` table relocate here too, alongside the chrome that reads them, rather than staying isolated in their own modules (`discord_roles.py`, and duplicated copies in `bot/discord_bot.py` and `cli/update_contests.py`).

The double-up-found builder keeps its existing gate, unchanged: a sport absent from `DISCORD_ROLE_MAP` gets no announcement sent at all, not just a missing role mention. This was confirmed during design to be intentional, existing scope — not a bug to fix.

Existing milestone wording (`"Contest starting soon (Nm)"`, `"Contest started"`, `"Contest ended"`, soft-finish's `"(updated)"` marker) is preserved verbatim, per the spec's wording-preservation clause, which names exactly these four milestone prefixes. Bonus-achievement and double-up-found are not in that list, and the spec separately asks (User Stories 5 and 6) for both to adopt "the same visual chrome (sport emoji, header style)" as the milestone kinds "even though" — for bonus-achievement — "they don't include a sheet link or entry fee," and so that double-up alerts "don't look like a leftover one-off format." Reformatting their message text is what those two stories ask for, not an exemption invented after the fact. The double-up-found builder still keeps every informational field the old one-liner carried (contest name, date, entry fee, entries) — it drops no data, it only reassembles it under the shared header/bullet chrome and adds the DK link the other five kinds already carry.

`CompletionProcessor`'s formatting methods now delegate to the shared builder instead of assembling text inline.

The interactive bot commands (`!contests`, `!live`, `!upcoming`) keep their own terser, synchronous-reply format — they are not broadcast announcements — but now pull `sport_emoji`/`sheet_link` from the shared module instead of a second, independently-maintained copy.

**Update (issue #133):** the above paragraph's scoping-out of `!contests`/`!live` is reversed for those two commands specifically. They now render through `build_milestone_announcement(prefix="Live", ...)`, the same builder the four automated milestone announcements use, instead of their own bespoke text — so an operator glancing at `!live` sees the same chrome as the automated "Contest started" push for that contest, rather than a third, differently-laid-out format. `!live`'s multiple per-contest blocks join with a blank line, matching `build_double_up_found_announcement`'s existing multi-contest join. The original terseness rationale is judged to matter less than that consistency for these two commands. `!upcoming` is unchanged and keeps the original terse rationale — it stays a dense, one-line-per-sport digest, not migrated to the bulleted chrome.

That reversal also gave `build_milestone_announcement` a new optional `vip_presence` keyword (`"present"` / `"absent"` / `None`, default `None`), rendered as a trailing `⭐ VIP: ...` bullet only when set. `!contests`/`!live` populate it from the VIP-presence verdict already cached in `contest_vip_presence` (via `NotificationStore.get_presence`) — no new DraftKings call. The four automated announcements that already gate on presence (warning, live, completed, soft-finish) leave it unset, so their wording is unchanged.

`lobby/formatting.py`'s `format_discord_messages` is a named exception, deliberately left outside this consolidation: it is not a Discord announcement at all, it feeds `logger.info(...)` in `cli/find_new_double_ups.py` for local operator visibility, and its output never reaches a Discord subscriber. The subscriber-facing double-up-found message goes entirely through `build_double_up_found_announcement`. Since this spec's problem statement and user stories are about what subscribers read on Discord, an internal log line carries no wording-consistency stake and stays a separate, one-line formatter rather than being folded into `discord_announcements.py`.

Named `discord_announcements.py` rather than a `discord/` package, deliberately deviating from the module name proposed during design: `tests/conftest.py` puts `src/dk_results` directly on `sys.path`, so a same-named `discord` package there would shadow the real, pip-installed `discord.py` library that `bot/discord_bot.py` imports (`import discord`, `from discord.ext import commands`). A flat module avoids the collision without changing the seam.

Out of scope, per the originating spec: `DiscordRest`/`WebhookSender` transport behavior (chunking, retries, bot-token vs. webhook), and the pre-existing duplicate `0009-*` ADR numbering collision (unrelated, not fixed here).
