# VipPresence consults the standings poll before scanning entrants

`VipPresence`'s only source of a presence verdict was an authenticated, paginated entrant-page scan (`ContestResultsPort.get_contest_entrants_page`) — capped at 50 pages, short-circuiting at the first tracked VIP found, returning `unknown_capped` when the cap is hit before a conclusive read. Meanwhile `SportProcessor` already parses the full standings CSV for every live contest each poll (ADR-0011) and persists `VipCashStatus` — one row per tracked VIP actually found in that poll — which is per-VIP-accurate for the *whole* field, not paginated or capped, since DraftKings' standings export includes every entrant with a locked lineup.

Decision: `VipPresence.verdict()` checks the standings poll first and only falls back to the entrant-page scan when nothing has been polled yet for that contest. This needed one new fact the schema didn't carry: `get_vip_cash_status` returning zero rows is ambiguous between "polled, no tracked VIP found" and "never polled" — `VipCashStatus.rank`/`points` being empty doesn't disambiguate either. A new `standings_polled_at` timestamp column on `contests`, stamped unconditionally by `SportProcessor` in the same call site as `set_cash_line` (guarded `ALTER TABLE` migration, matching ADR-0011's own pattern), resolves it: `None` means "not polled, fall through"; a timestamp means the standings answer is authoritative in both directions.

The standings dependency is expressed as a new narrow protocol, `StandingsPresencePort` (`get_standings_polled_at`, `get_vip_cash_status`), not the full `ContestDatabase` — matching how `VipPresence` already models its DraftKings dependency as the minimal `ContestResultsPort` rather than a general client. `ContestDatabase` satisfies it structurally.

`VipPresence` also gained `present_vips(dk_id, vip_names) -> list[str]`, the per-VIP breakdown the standings source makes available almost for free (`get_vip_cash_status` already returns one row per matched VIP). `verdict()`'s standings branch is `present` iff this is non-empty, else `absent`. This is a standings-only capability: the entrant-page scan short-circuits at the first match by design (ADR-0011 rejected enumerating a full field there on cost grounds), so it can never answer "which VIPs," only "at least one." Nothing outside `VipPresence` consumes `present_vips` yet — threading it into announcement or `!live` text is explicitly out of scope here.

Caching: a standings-derived `present` writes through to `NotificationStore`, matching the existing invariant that a cached `present` is permanent and never rechecked. A standings-derived `absent` is not cached. The entrant-scan's cached `absent` carries a refresh timer (`VIP_ABSENT_REFRESH_MINUTES`) sized for the cost of re-scanning; the standings answer has no such cost; caching it anyway would plant a second, timer-less "absent" in the same store the entrant-scan's policy governs, with no way for a direct reader (`discord_bot.py`'s `_vip_presence_for_contest`) to tell which policy produced it.

No behavior change to the suppression policies themselves (ADR-0008): `verdict()`'s external interface and the four verdicts are unchanged, so `_presence_blocks_start` and `_presence_absent` are untouched. What changes is how often the answer comes from a DraftKings call at all — for any sport `CompletionProcessor` tracks, `SportProcessor` polls the identical live contest (both resolve `get_live_contest` from the same `get_sport_choices()`, with identical `sheet_min_entry_fee`/`keyword` arguments), so this isn't contest-set-dependent: once a contest has had one `SportProcessor` poll since going live, `live`/`completed`/`soft-finish` presence checks resolve from SQLite, not DraftKings. The entrant-page scan remains the only source pre-start (`warning`) and in the brief gap between a contest going live and its first poll — ADR-0008's no-retry policy is preserved there unchanged.

Out of scope: threading `present_vips` into announcement text or `!live`'s display (a follow-on once the building block exists); revisiting the entrant-scan's own cap/refresh policy, which this doesn't touch.
