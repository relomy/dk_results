# Persist the standings cash line for mid-contest VIP-cashing visibility

Issue #134 asked whether "is a tracked VIP currently cashing" can be answered mid-contest without a new per-command DraftKings call. Today that question is only ever answered by `CompletionProcessor._maybe_send_soft_finish_announcement`, which calls the authenticated leaderboard endpoint and only runs once `_soft_finish_eligible` holds — effectively at/near the very end of the contest. The bot process itself (`bot/discord_bot.py`) makes zero DraftKings calls and reads only `ContestDatabase`.

`SportProcessor` already parses the full standings CSV for every live (started, not-yet-completed) contest on its own independent poll (currently every 5 minutes), and `_update_cash_stats` (`domain/contest_standings.py`) already derives, in memory, the last paid position and its score (`min_rank`/`min_cash_pts`) from `positions_paid` and each row's rank/points — the exact "cash line" the issue's theory describes. It also already retains every user's own rank/points, including a `vip_list` pre-filtered to tracked VIP names. None of this required a new network call; it was already being computed and thrown away except for a write to the Google Sheet.

Decision: persist the cash line — not the full standings — as two new columns on `ContestDatabase.contests` (rank and points of the last paid position), overwritten on every `SportProcessor` poll. `SportProcessor` was read-only against `ContestDatabase` before this (it only called `get_live_contest` to find its target); this gives it its first write path into that table.

The cash line alone isn't enough for `!live` to render a per-VIP verdict: a VIP's own standings rank only exists in `SportProcessor`'s in-memory `ContestStandings.vip_list` at parse time, and the bot process that serves `!live` reads only `ContestDatabase` — it has no other route to that fact. So each tracked VIP's own rank/points is persisted too, as one row per VIP per contest (`VipCashStatus`: `vip_name`, `rank`, `points` — a named frozen shape, following the `ContestRow` precedent from ADR-0006), in a new table rather than fixed columns on `contests`: the VIP list is arbitrary-cardinality and one-to-many against a contest, so baking it into fixed columns would make the schema mirror the data's variable shape instead of hiding it. The write side is a single method, `ContestDatabase.replace_vip_cash_status(dk_id, statuses)`, that atomically replaces the full set for a contest each poll — matching how `SportProcessor` re-parses the whole VIP list every cycle rather than updating it incrementally — paired with `get_vip_cash_status(dk_id)` for reads. `!live` then adds one bullet per row returned for that contest, comparing each VIP's own rank against the persisted cash-line rank at read time; the per-VIP *verdict* is still computed at read time and never persisted, only the underlying rank/points fact is.

Terminology: the cash line is a positional/scoring cutoff derived from `positions_paid`, and is deliberately kept distinct from the existing **Cashing** glossary term, which means a realized, positive payout. A row at or above the cash line is only *projected* to cash — it can still be wrong (ties, late-contest volatility) until `CompletionProcessor`'s soft-finish leaderboard check confirms it from real payout data. `!live`'s bullet is explicitly a provisional estimate, no fresher than the last `SportProcessor` poll.

Alternatives considered and rejected:
- Making the bot (or some new on-demand path) call the DraftKings leaderboard directly when asked. This is exactly the new architectural seam issue #134 identified as the expensive option: authenticated DK calls and auth handling from a process that currently has none.
- Reading the cash line back out of the Google Sheet, which `SportProcessor` already writes it to (`sheet.add_min_cash`). Rejected because the bot has no Google Sheets client or auth today; adding one only to read back a value the same process already computed would be a heavier, more roundabout seam than a same-process SQLite write.

No migration mechanism previously existed for `ContestDatabase`'s schema (`create_table` is a single `CREATE TABLE IF NOT EXISTS`, so new columns only land on a fresh database file). This change adds a small guarded migration — checking `PRAGMA table_info(contests)` and issuing `ALTER TABLE contests ADD COLUMN` for the two new cash-line columns if not already present — rather than requiring an out-of-band manual step against already-deployed database files. The new `vip_cash_status` table needs no such migration: it's a `CREATE TABLE IF NOT EXISTS` in its own right, which is safe against both a fresh and an already-deployed database.

Out of scope: `dfs-common`'s mirrored `contests` table, which carries only contest lifecycle metadata (no standings/leaderboard data) and is unrelated to this feature; unifying the two independent VIP-list loaders (`vip_lineups.load_vips` vs. `update_contests._load_vips`), which predates this change and isn't touched by it.
